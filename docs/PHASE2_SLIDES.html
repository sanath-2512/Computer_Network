TEAM 1 HTTP CACHING SLIDE 7 OF 18

HTTP Caching Mechanics: ETag & 304 Not Modified

RFC 9110 conditional validation saving wireless LAN bandwidth

  • Initial Request (HTTP 200): Client requests static resource; Nginx computes ETag (e.g. "674...-100") and Cache-Control.
  • Client Local Cache: Client stores representation and caches the ETag validator.
  • Conditional Request (HTTP 304): Client sends If-None-Match with stored ETag.
  • Zero-Body Response: Nginx confirms content has not changed; returns HTTP/2 304 Not Modified with Content-Length: 0.
  • Bandwidth Conservation: Eliminates duplicate payload transfer over wireless LAN.
Initial HTTP 200 response with ETag header followed by conditional HTTP 304 Not Modified response.

TEAM 1 EXTENSION B SLIDE 9 OF 18

Extension B: Dynamic TTL & Controlled DNS Cutover

Optimizing DNS cache expiration for rapid disaster recovery propagation

  • The TTL Trade-off: High TTL (e.g. 24h) minimizes DNS query overhead but causes slow failovers; low TTL (5s) floods wireless LAN.
  • Phase 2 Design Choice: 30-Second TTL provides sub-minute disaster cutover with minimal wireless overhead.
  • TTL Countdown: Consecutive dig queries display TTL counting down: 30s -> 25s -> 12s -> 0s.
  • Controlled Cutover: DNS record updated and client cache flushed via dscacheutil -flushcache && sudo killall -HUP mDNSResponder.
  • Negative Caching: min-cache-ttl=0 configured to prevent persistent caching of transient lookup errors.

TEAM 1 EXTENSION C SLIDE 10 OF 18

Extension C: Kernel-Level Service Isolation (macOS PF)

Enforcing zero-trust perimeter around backend services using macOS PF

  • The Vulnerability: If raw backends listen on LAN interfaces, any unauthorized user can bypass Nginx security.
  • Defense-in-Depth: Backends bound to 127.0.0.1 AND protected by macOS Packet Filter (pfctl) kernel anchor.
  • PF Anchor Rules (com.apple/team1_isolation):
  • • block in quick on en0 proto tcp to any port {3001, 3002}
  • • pass in quick on lo0 proto tcp to any port {3001, 3002}
  • • pass in quick on en0 proto tcp to any port {80, 443}
  • Empirical Proof: nc to 10.7.11.108:3001 times out (dropped by PF), while port 443 connects instantly.
Firewall verification: nc probe to ports 3001/3002 times out while HTTPS port 443 succeeds.

TEAM 1 PRODUCTION HARDENING SLIDE 15 OF 18

Production Hardening & Architectural Trade-offs

Critique of design decisions, scaling bottlenecks, and real-world datacenter practices

Health Checking Mechanisms
  • Our Architecture: Nginx OSS passive health checks (max_fails=2, fail_timeout=10s).
  • Trade-off: Requires 1-2 failed client requests before an upstream is marked down.
  • Enterprise Production: Envoy / Nginx Plus active synthetic probes (health_check uri=/api/health).
  • Proactively removes failed servers before client requests ever experience latency.
Edge Routing & Failover
  • Our Architecture: DNS-based failover with 30s TTL and dual resolver entries.
  • Trade-off: Dependent on client resolver implementation and OS cache flushing.
  • Enterprise Production: BGP Anycast routing where both nodes announce identical Virtual IP (VIP).
  • Sub-second failover at Layer 3/4 via ECMP router re-convergence with zero DNS delay.
Zero-Trust Upstream Security
  • Our Architecture: macOS PF firewall + loopback binding for upstream isolation.
  • Enterprise Production: Mutual TLS (mTLS) with client certificates between Edge and Backends.
  • Cryptographic identity guarantees only authenticated proxies can decrypt backend traffic.
  • Automated Certificate Lifecycle: ACME protocol / HashiCorp Vault automated rotation.

TEAM 1 VIVA DEFENSE GUIDE SLIDE 17 OF 18

Viva Defense: High-Scoring Technical Model Answers

Precision technical rationale for top examiner questions

Q1: Defense-in-Depth for Backends
  • Q: Why bind backends to 127.0.0.1 AND use PF firewall?
  • A: Defense-in-depth principle. If a backend is accidentally bound to 0.0.0.0 or if an unauthorized process binds to a public port, the kernel PF packet filter guarantees incoming packets on en0 are silently dropped before reaching the application layer.
Q2: macOS DNS Resolver Failover
  • Q: How does macOS resolver handle dual DNS entries?
  • A: mDNSResponder maintains affinity to the first nameserver (10.7.9.214). Upon query timeout, the resolver marks the primary as degraded, falls back to the secondary (10.7.11.108), and caches that failover state until the primary recovers.
Q3: TLS 1.3 vs TLS 1.2 Handshake Latency
  • Q: Why is TLS 1.3 faster than TLS 1.2 during connection setup?
  • A: TLS 1.2 requires 2 full round-trips (2-RTT) for negotiation and key exchange. TLS 1.3 completes in 1-RTT because the client speculatively sends its Diffie-Hellman key share inside the ClientHello message.
